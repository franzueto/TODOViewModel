Improve the TODO app with ViewModel and State

    1. Overview

    In this codelab you'll take a small TODO app where everything lives inside a single composable and restructure it into a ViewModel, a UI state class and a repository.

    My tasks
    1 of 2 remaining
    New taskAdd
    Buy milk
    Study ViewModel

    What you'll build

    The same TODO app, with the same features (add, complete and delete tasks), but now:

    • Tasks survive screen rotation and other configuration changes.
    • The UI only draws state and reports events.
    • The logic can be unit tested without an emulator.
    • Previews can show any state you want.

    What you'll learn

    • Why state stored with remember is lost when the Activity is recreated.
    • How a ViewModel keeps state across configuration changes.
    • How to model a screen with a single, immutable UI state class.
    • How a repository becomes the single source of truth for your data.
    • How to expose state with StateFlow and collect it with collectAsStateWithLifecycle().
    • How to split a composable into a stateful and a stateless version.
    • How to unit test a ViewModel.

    What you'll need

    • The latest stable version of Android Studio.
    • An emulator or device running Android 7.0 (API 24) or newer.
    • Basic knowledge of Kotlin and Jetpack Compose (@Composable, remember, Column, LazyColumn).

    Why does this happen?

    Open ui/TodoScreen.kt. All of the screen's state is created inside the composable:

    remember keeps a value across recompositions, but not across configuration changes. When the device rotates, Android destroys the Activity and creates a new one, so the composition starts from scratch and every remember runs again with its initial value.

    Rotation isn't the only configuration change. The same happens when the user switches to dark mode, changes the language, resizes the window in multi-window mode or unfolds a foldable.

    Other problems with this code

    • UI and logic are mixed. Generating ids, trimming and validating input and updating the list all happen in the same function that draws the UI.
    • It's hard to test. To check that a blank task is ignored you would need to run a UI test.
    • It's hard to preview. TodoScreenPreview can only show an empty list, because the composable creates its own data.
    • The data has nowhere to grow. Saving tasks to a database later would mean changing the UI code.
    What about rememberSaveable? It survives configuration changes by saving values into a Bundle. It's great for small pieces of UI state, like the text being typed, which you'll use it for later. It isn't meant for your app's data. A list of custom objects would need a custom Saver, and Bundles have a small size limit.

    3. Plan the new architecture

    You'll split the screen into layers. Each layer has one job, and data moves in a single direction. This is called unidirectional data flow (UDF):

    UI layerTodoScreenDraws the state and reports events
    events →← UI state
    State holderTodoViewModelSurvives configuration changes and produces TodoUiState
    calls →← data
    Data layerTodoRepositorySingle source of truth for the tasks
    • State flows up. The repository holds the tasks. The ViewModel turns them into a TodoUiState, and the UI draws it.
    • Events flow down. When the user taps something, the UI calls a ViewModel function, which updates the repository.

    The UI never changes the data directly. There is exactly one place where tasks are changed, which makes the app easier to reason about and to test.

    Files you'll create

    FileWhat it does
    data/Todo.ktThe Todo data model, moved out of the UI.
    data/TodoRepository.ktStores the tasks and exposes them as a StateFlow.
    ui/TodoUiState.ktAn immutable snapshot of what the screen shows.
    ui/TodoViewModel.ktConnects the repository to the UI and handles events.
    ui/TodoScreen.ktModified: split into a stateful and a stateless composable.

    6. Create the repository

    The repository is the single source of truth for the tasks. It's the only class that stores and changes them. Everything else reads them through it.

    Create a new file TodoRepository.kt in the data package:

    How it works

    MutableStateFlow and StateFlow
    A StateFlow always holds a current value and notifies its collectors whenever the value changes. The Mutable version can be changed, so it's kept private. Other classes get a read-only StateFlow through asStateFlow(). This is called a backing property, which is why the private one starts with an underscore.
    _todos.update { ... }
    Computes the new value from the current one and replaces it safely, even if several updates happen at the same time.
    Immutable lists
    The repository never mutates a list. todos + newTodo, map and filterNot all return a new list. A StateFlow only emits when the new value is different from the old one, so creating new lists is what makes the change visible.
    nextId
    Generating ids is data logic, so it moves from the UI to the repository.
    The tasks are still kept in memory. Because only the repository knows how they are stored, you could later back it with a database (for example, Room) without changing a single line of UI code.

    7. Create the UI state class

    A UI state class describes everything the screen needs to draw itself, in one immutable object. Instead of reading several separate variables, the UI receives a single TodoUiState and draws it.

    Create TodoUiState.kt in the ui package:

    Why a separate class?

    • One snapshot. The screen always draws a consistent state. It can't see an updated list with an outdated counter.
    • Derived values live in one place. remainingCount and isEmpty are computed from todos, so they can never get out of sync. Before, this logic was mixed into the composable.
    • Easy to fake. Previews and tests can create any state they want, for example TodoUiState(todos = listOf(...)).
    Use val for every property and a data class, so the state is immutable and two states with the same content are equal.

    8. Create the ViewModel

    A ViewModel is a state holder that survives configuration changes. When the Activity is recreated after a rotation, the new Activity receives the same ViewModel instance, together with all of its data. The ViewModel is only cleared when the screen is finished for good, for example when the user presses back to leave it.

    Create TodoViewModel.kt in the ui package:

    How it works

    repository: TodoRepository = TodoRepository()
    The ViewModel receives the repository through its constructor. The default value means the app can create the ViewModel without arguments, while tests can still pass in their own repository.
    map { todos -> TodoUiState(todos = todos) }
    Every time the repository emits a new list, it's turned into a new TodoUiState.
    stateIn(...)
    Converts that flow into a StateFlow the UI can read:
    • viewModelScope ties the work to the ViewModel's lifetime and cancels it automatically when the ViewModel is cleared.
    • SharingStarted.WhileSubscribed(5_000) keeps the flow active while the UI is collecting it, plus 5 seconds afterwards. A rotation takes less than that, so nothing restarts. If the app stays in the background, the work stops.
    • initialValue is what the UI sees before the first value arrives.
    addTodo, toggleTodo, deleteTodo
    These are the events the UI can send. Notice that the rules about blank and untrimmed titles moved here from the composable. That logic is now plain Kotlin that you can test.
    Never keep a reference to an Activity, a Context or a View inside a ViewModel. The ViewModel lives longer than they do, so it would keep the old, destroyed Activity in memory.

    What changed?

    viewModel: TodoViewModel = viewModel()
    viewModel() returns the existing ViewModel for this screen, or creates one the first time. After a rotation, it returns the same instance.
    collectAsStateWithLifecycle()
    Reads the StateFlow as Compose State, so the UI recomposes whenever a new TodoUiState is emitted. It also stops collecting while the app is in the background.
    onAddTodo = viewModel::addTodo
    A function reference. When TodoContent calls onAddTodo("Buy milk"), the ViewModel's addTodo runs. The UI only reports what happened. It doesn't decide what to do about it.
    rememberSaveable for the text field
    The text being typed is UI element state: it only matters to this screen while it is visible, and no business logic depends on it. It's fine to keep it in the UI, and rememberSaveable makes it survive configuration changes. The tasks are app data, so they live in the repository.
    Two previews
    Because TodoContent is stateless, the previews can show both an empty list and a list with completed tasks, without running any logic.
    MainActivity doesn't need to change. It still calls TodoScreen(modifier = ...), and the ViewModel parameter uses its default value.

    10. Run and verify

    Run the app and repeat the experiment from the beginning. Check each item as you go:

    Everything works.

    What happened during rotation?

    1. Android destroyed the Activity and created a new one.
    2. The new composition called viewModel(), which returned the existing TodoViewModel.
    3. collectAsStateWithLifecycle() immediately received the current TodoUiState, so the list was drawn again.
    4. rememberSaveable restored the typed text from the saved instance state.
    Still kept in memory. If the user leaves the screen with back, or the system kills the app's process in the background, the tasks are lost. Fixing that means storing them on disk, for example with Room. Thanks to the repository, that's a data-layer change only.

    12. Congratulations

    You restructured the TODO app using recommended Android architecture:

    • A repository is the single source of truth for the data.
    • A UI state class describes the screen in one immutable object.
    • A ViewModel survives configuration changes, owns the screen's logic and exposes state as a StateFlow.
    • A stateless composable only draws state and reports events, which makes it easy to preview.
    • Unit tests check the logic without a device.

    Practice

    Try adding new features by following the same flow, data layer first and UI last:

    1. Clear completed. Add clearCompleted() to the repository and the ViewModel, a hasCompleted property to TodoUiState, and a button that is only visible when hasCompleted is true. Write a test for it.
    2. Filter. Let the user show All, Active or Completed tasks. Where should the selected filter live? Should the filtering happen in the repository or in the ViewModel?
    3. Persist the tasks. Back TodoRepository with a Room database so that tasks survive the app being closed. The UI and the ViewModel shouldn't need to change.
